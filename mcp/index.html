Every AI app needed its own plug

MCP replaces one-off integrations with a shared protocol. It started inside Anthropic and now lives under neutral governance.

The problem

By 2024, language-model apps could call tools, but every connection was custom. If Claude, an IDE and your own app all needed to read the same repository or database, someone built that glue three times. With N apps and M tools that is N × M integrations, and each new app or tool makes the pile bigger.

The idea

MCP, the Model Context Protocol, borrows its approach from the Language Server Protocol that editors use. A tool describes itself once as an MCP server. Any app that speaks the protocol, an MCP client, can then discover and use it. The work drops from N × M to N + M.

From side project to standard

When What happened
Nov 2024 Anthropic open-sources MCP with the first spec, 2024-11-05, plus SDKs and reference servers.
Mar 2025 Revision 2025-03-26 introduces Streamable HTTP, replacing the older HTTP+SSE transport.
Jun 2025 Revision 2025-06-18 adds structured tool output and elicitation, and treats servers as OAuth resource servers.
Nov 2025 Revision 2025-11-25 adds OpenID Connect discovery, URL-mode elicitation, Client ID Metadata Documents and experimental Tasks.
9 December 2025 MCP is donated to the Agentic AI Foundation, a directed fund under the Linux Foundation. Anthropic, Block and OpenAI co-found it.
28 July 2026 Revision 2026-07-28 is final: the largest rewrite since launch, and the subject of most of this guide.

At the time of the donation MCP had more than 10,000 active servers and over 97 million monthly SDK downloads. The maintainer structure stayed the same, and the foundation does not set the protocol’s technical direction.

Is it an official standard?

MCP is an open protocol governed by its own proposal process (Specification Enhancement Proposals), not an IETF or ISO standard. It builds on standards that are: JSON-RPC 2.0, OAuth 2.x and OpenID Connect.

How MCP is put together

Three roles, three things a server can offer, one message format, and two ways to carry it.

Host, client, server

  • The host is the app the person uses: Claude, an IDE, your own agent.
  • The host runs one MCP client for each server it connects to.
  • The server is a small program that exposes what a system can do, such as Azure DevOps, a database or the file system.

Three things a server can offer

Each one has a different owner, which decides who triggers it.

Primitive Controlled by What it is Example
Tools The model Actions the model can call Create a work item
Resources The app Data the app can read and attach A file, a query result
Prompts The user Reusable templates the user picks A slash command

One message format: JSON-RPC 2.0

Every message is JSON-RPC. A request names a method and params and carries an id. The response repeats the id and holds either a result or an error. A message with no id is a notification and gets no reply.

JSON-RPC only defines the shape of a message. How it travels is the transport’s job.

Two ways to carry it

stdio is for local servers. The client starts the server as a subprocess, writes messages to its standard input and reads replies from its standard output. There is no network and no port, so it is fast and simple, but it only works on the same machine.

Streamable HTTP is for remote servers. The server exposes one endpoint, for example /mcp. Every message is an HTTP POST. The server answers with a plain JSON body, or upgrades that response to a Server-Sent Events stream when it needs to send progress or several messages. It replaced the older two-connection HTTP+SSE design, which was awkward for proxies and scaling.

The session is gone

The 2026-07-28 revision makes MCP stateless at the protocol level, so a server can scale like any other HTTP API.

Breaking change in 2026-07-28

This revision is not backward compatible. If you run or build a server, check that your SDK supports it before you upgrade clients.

What the session cost

Until 2025-11-25, every connection began with an initialize handshake. The server could answer with an Mcp-Session-Id, and the client had to send that id on every later request. That pinned the client to one server instance, so a load-balanced deployment needed sticky routing or a shared session store.

What changed

Concern Until 2025-11-25 2026-07-28
Starting initialize, then initialized No handshake. Each request carries its protocol version, client info and capabilities in _meta
Session The server may issue Mcp-Session-Id No protocol session and no header
Learning what a server offers Capabilities from initialize, then tools/list server/discover in one call, or tools/list
Change notifications An HTTP GET stream and resources/subscribe subscriptions/listen with a filter
The server needs input The server sends a request to the client mid-call The server asks, the client retries the call with inputResponses
A broken stream Resume with Last-Event-ID No resume. Send the request again
Routing Read the body or pin to an instance Mcp-Method and Mcp-Name headers, so gateways can route without parsing JSON
Caching Not specified ttlMs and cacheScope on list and discover results

Where state goes now

Stateless at the protocol layer does not mean your application has no state. A server that needs memory across calls hands out an explicit handle, such as a basket id, and the model passes it back as an ordinary argument. The model can see it, reason about it and pass it between tools, which a header hidden in the transport never allowed.

Pushing without a session

The client sends one subscriptions/listen request with a filter that says what it wants to hear about. The response stays open and carries matching events, each tagged with a subscription id. Progress and log messages for a single call still travel on that call’s own response.

Readers who know SignalR will see the similarity: both push server events over a long-lived HTTP connection. The differences matter.

SignalR MCP subscriptions/listen
Direction Two-way on one connection Server to client. The client sends new requests separately
Connection state Connection ids, groups, hub state None. The filter lives in the request
Reconnect Built in Open a new request and refetch
Scaling A backplane to fan out across instances Only streams need fan-out. Ordinary calls need nothing

Removed and deprecated

Check your clients and servers

Removed in this revision: the initialize handshake, session ids, resumability, ping and resources/subscribe. Deprecated: roots, sampling and logging. Tasks moved out of the core specification into an official extension, and a new extensions framework lets extensions version independently of the core.

One tool call, end to end

How a client finds out what a server offers, how the model picks a tool, and what comes back.

The client does not need to know in advance

A server describes itself at runtime. In 2026-07-28 a client can call server/discover and get the protocol version, capabilities and tool list in one response. tools/list still works and is the normal path when a server does not offer discovery. Responses carry ttlMs and cacheScope hints so clients and gateways can cache the catalog.

Before 2026-07-28 the order was initialize first, then tools/list, resources/list and prompts/list.

Each tool describes its own input

The model reads these descriptions and schemas, matches your request to a tool, and writes arguments that fit inputSchema. Nothing about the format is hard-coded in the client.

What comes back

A tool result holds a content array of typed blocks.

Block Carries
text A string. Servers often put JSON, Markdown, CSV or logs inside it.
image and audio Base64 data plus a MIME type.
resource_link A URI the client can fetch later, which avoids sending large data inline.
Embedded resource A resource with either text or a base64 blob and a MIME type.

A tool can also declare an outputSchema and return structuredContent, validated JSON that a client can parse directly. isError marks a failure inside the tool, as opposed to a protocol error.

Who turns data into a table

The spec enforces the block types and, when a schema is declared, the shape of structuredContent. It does not look inside a text block. There is no table type. A server returns rows as structured JSON or as text, and the model or the client renders them the way you asked, as a table, a summary or a chart.

Binary data is base64 inside JSON, so keep it small or send a resource link.

Security: who may call what

MCP does not invent its own login scheme. It uses HTTPS and OAuth, and sets rules for how servers and clients use them.

The transport

  • stdio has no network, so there is no TLS. Trust comes from you choosing to run that process, so run only servers you trust.
  • Streamable HTTP is plain HTTPS. TLS gives encryption and server identity. A server listening on localhost should check the Origin and Host headers so a web page cannot reach it through DNS rebinding.

Authorization is optional, and standard when used

For a protected remote server, MCP follows OAuth 2.1 and OpenID Connect. The server is an OAuth resource server.

  1. The client sends a request and gets 401 with a pointer to the server’s Protected Resource Metadata (RFC 9728).
  2. That metadata names the authorization server. The client signs the user in there using the authorization code flow with PKCE.
  3. The token is issued for this server only, using Resource Indicators (RFC 8707), so the server must check the audience.
  4. The client sends Authorization: Bearer <token> on every request, never in the URL.
  5. The server validates the token and the scope on every call. Hiding a tool from a list is a convenience, not a check.

When a server wants more access than the token has, it answers 403 and the client can ask for a broader scope. This is incremental scope consent.

Authorization hardening in 2026-07-28

Six proposals align MCP with how OAuth is deployed. Clients must validate the iss parameter on authorization responses (RFC 9207) and bind registered credentials to the issuing authorization server. This matters because one client talks to many authorization servers, which makes mix-up attacks easier. Client ID Metadata Documents now come before Dynamic Client Registration, which is deprecated, and refresh-token guidance covers OpenID Connect style servers.

Client registration follows this order when a client supports every option: pre-registered credentials, then Client ID Metadata Documents, then Dynamic Client Registration as a fallback, then asking the user.

Where the token lives

The spec leaves storage to the client app. Good clients use the operating system’s secure store, or an encrypted secrets store on a server, and keep tokens per user and per MCP server. Access tokens are short-lived and renewed with a refresh token, so a restarted app does not ask the user to sign in again.

In MCP’s OAuth model the host application holds the credential. When a sub-agent calls a tool, the safe pattern is that the host’s client attaches the token and the sub-agent never sees it. The catch is that the sub-agent then has the host’s full access to that server. To give each hop narrower access, use token exchange (RFC 8693) in your own design. MCP does not prescribe it.

Ways it goes wrong

Problem What happens Defence
Confused deputy A proxy server that uses one OAuth client toward a third-party service is tricked into granting access to the wrong party Per-client consent and strict redirect URI validation
Token passthrough A server accepts a token that was not issued for it and forwards it downstream. The spec forbids this Validate the audience, and use a separate token for each hop
DNS rebinding A web page reaches a server running on localhost Validate Origin and Host, and bind to localhost
Authorization server mix-up A client is redirected to a hostile authorization server Validate iss and bind credentials to the issuer
Prompt injection and tool poisoning Text in a tool description or result tries to steer the model Vetted servers, least privilege, human approval for risky actions

What OAuth does not cover

OAuth decides whether a client gets a token for a server. It says nothing about what a tool does afterwards. A malicious but properly authorized server, an over-broad scope or an injected instruction is still your responsibility.

Building and choosing

A first server in C#, how to test it, and how to pick a language.

A first server in C#

An ASP.NET Core server needs one package, one tool class and one endpoint. Stateless mode matches the 2026-07-28 model: no session, so any instance can answer.

Check the SDK version

This sample is not compiled as part of this repo. API names and defaults change between SDK releases, so check the notes for the version you install, and confirm it supports 2026-07-28.

For a local server instead, host the same tools with the stdio transport and let the client launch the process.

Test it with the Inspector

The MCP Inspector lists a server’s tools and lets you call them and see the raw JSON-RPC. Run it with npx @modelcontextprotocol/inspector, then point it at your server’s command or URL.

Choosing a language

Anything that can speak JSON-RPC over stdio or HTTP can host a server, so the choice is about SDK maturity and your team.

Language A good fit when
C# and .NET Your logic already lives in .NET and you want ASP.NET Core hosting, auth and DI
TypeScript You want the reference SDK and the most examples, or fast prototyping
Python The integration is data, ML or scripting work
Java and Kotlin Enterprise back ends, with Spring or Quarkus integrations
Go Small, fast, single-binary servers
Rust Performance or a tiny footprint
Ruby, PHP and Swift You already work in that stack and its SDK covers what you need

Check each SDK’s release notes for support of 2026-07-28 before committing.

Mind the context cost

Every tool’s name, description and schema is sent to the model, so connecting many servers, or one large server, uses up context and can make the model pick the wrong tool. Enable only the tools a task needs.

Before you ship

A short checklist, and where to keep learning.

A checklist for an MCP server

  • Name tools for what they do, and describe every input. The model reads these words.
  • Return structuredContent with an outputSchema when a client needs to parse the result.
  • Keep results small. Send a resource_link for large data.
  • Do not keep state in memory between calls. Hand out explicit ids instead.
  • Require OAuth for anything remote. Validate signature, expiry, audience and scope on every call.
  • Never forward a client’s token to another service. Get a separate token for that hop.
  • Give each token the least scope it needs, and ask for more only when a call requires it.
  • Treat everything a tool returns as untrusted text before it reaches a model, and ask a person before risky actions.
  • Test with the Inspector, then with a real client.
  • Pin the spec revision you target and watch for the next one.
